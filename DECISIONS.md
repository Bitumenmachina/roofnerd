# Decisions

One line each: what was decided, and why. Calls made during the build that the handoff
did not cover. Newest last.

| # | Decision | Why |
|---|---|---|
| D1 | The build handoff lives in `refs/` with the other two ruling documents | `refs/` is gitignored and the handoff is the third document of its kind. It carries no client data, but the smaller boundary is the right default for anything that rules the build. |
| D2 | `STATUS.md`, `DECISIONS.md`, `QUESTIONS.md`, `DEPENDENCIES.md` are public | They carry no client data, and a contributor reading the repo cold should see what was decided and what is open. Client-identifiable material never enters them. |
| D3 | `SF` is a real number only for an **area** condition. A run becomes an area through a formula — `LF * H` — never behind the estimator's back | The handoff's own worked example writes it that way. Two routes to the same number is how a line gets counted twice, and the height stays visible on the line instead of buried in a function. |
| D4 | The open document is keyed by PART NAME — `job`, `pages`, `conditions`, `costCodes` — not by file path | A JSON Pointer splits on `/`, so a key like `pages/pages.json` reads as two steps and can never be addressed. Windows now say `/pages/0/feetPerUnit`, which is what it should have looked like anyway. Found by the section 1 probe; it was latent in the Rust side too. |
| D5 | No Vite dev server. The front end builds to static files and the shell serves them over its own protocol in development exactly as in a release | It makes the content security policy live while working. A dev server would leave the local-only claim untested until a release build, which is the wrong way round for the one property the program is publishing its source to prove. |
| D6 | Probes drive the real built front end in headless Chrome (`puppeteer-core`), with only the shell stubbed | A done-check the executor can run itself, rather than a description of one. Everything above the shell boundary — editors, surface, tools, engine — is the shipped code unmodified. |
| D7 | `page.render()` is cancellable and paints are serialized; the overlay is sized before the paint, not after | pdf.js refuses two paints on one canvas, which is exactly what leaning on the zoom key asks for. Sizing the overlay first also means a trace is correctly placed while a big sheet is still drawing underneath it. |
| D8 | The dialog plugin is in; there is no file-system plugin | Picking a drawing needs the operating system. Reading one does not: `read_page_source` resolves inside the open job and refuses anything outside it, so a window cannot name a file anywhere on the machine and have this program read it out. |
| D9 | A drawing that fails to open says so on the hint line | A blank sheet with no explanation is the worst thing the editor could do — the estimator would trace nothing and never learn the file was the problem. |
| D10 | Tracing another shape while a condition is selected adds it to that condition | It is how a parapet gets traced: three runs, one condition. A new condition per stroke would make the estimator merge them by hand every time. Tracing with nothing selected still starts a new one, so neither habit is blocked. |
| D11 | Money is charged on what gets BOUGHT, not on what gets installed | If it is sold by the sheet, the bid pays for whole sheets. Pricing the installed quantity and ordering the rounded one is how a job runs short on material and long on margin — on paper. |
| D12 | A price typed on the line beats the scenario's price book | A price on the line is a quote in hand; the scenario is the book. The specific beats the general, and it is visible on the line either way. |
| D13 | Quantities are settled to nine decimal places where they meet a rounding step | `100` with 10% waste is `110.00000000000001` in binary floating point, and a bare `ceil` turns that into twelve rolls instead of eleven. Nine places is far below anything measured and far above the noise. Found by a test; pinned by one. |
| D14 | The formula column is the widest on the sheet, and the table has fixed columns | A formula clipped at a column edge is a formula nobody can check, which is the exact failure this program was started to leave behind. |
| D15 | `EA` on a line or area condition is the vertex count; an arc contributes none. `VERTICES` and `SEGMENTS` are separate named measures | Read off real drawing reports rather than guessed: a closed rectangle traced a dozen times counts four corners each time, and a single arc counts none while still carrying a length. Closes Q1. Addendum §1. |
| D16 | The rounding rule lives in `packages/engine/src/rounding.ts` and every step that rounds a quantity goes through it — the order-unit step, and `ceil`/`floor`/`round` typed into a formula | Nine decimal places, stated as `SETTLE_PLACES`. Settling decides the number that was *intended* before the rounding decides the answer. Applied everywhere rather than only where the defect was found. Addendum §7. |
| D17 | A section is not done on Chrome. From section 3 on, the done-check runs against the release binary under `tauri-driver` — WebKitGTK rendering, the Rust shell, real OS windows | Blink with a stubbed shell is not what an estimator runs, so passing there is not evidence about the thing that ships. The Chrome harness stays for building and for engine unit tests. Addendum §2. |
| D18 | The WebDriver client is written out (about sixty lines of `fetch`) instead of using `webdriverio` | `tauri-driver` wants the capabilities exactly as the specification writes them, and the client library reshaped them into a mismatch that reported as "failed to match capabilities" — with the raw payload working under `curl`. Fewer moving parts, one less dependency. |
| D19 | The content security policy is checked in the shipped runtime at the end of every section, and the result is written into `evidence/` with the commit it came from | It had been asserted twice and tested never. `fetch('https://example.com')` is refused by policy; `fetch('/index.html')` returns 200. Addendum §3 and §4. |
| D20 | The release bundle runs as `pnpm build:app`, which sets `NO_STRIP=true` | linuxdeploy's bundled `strip` predates the `.relr.dyn` sections Fedora's toolchain emits and fails the AppImage on every system library. `NO_STRIP` is linuxdeploy's own escape; the cost is an unstripped, larger AppImage and nothing else. |
| D21 | An item carries three units — estimating, order, price — each with its own conversion and its own rounding rule | A real supply house quotes membrane by the square foot, sells it by the roll, and you estimated it in squares. Collapsing that into one conversion is where a bid quietly gains or loses money. Addendum 2 §1. |
| D22 | A conversion may be written `per` (four rolls to a box) or `contains` (a thousand square feet in a roll) | Both directions occur in real catalogues and neither is the odd one out. They are the same fact from either end, and the estimator should type whichever they are looking at. |
| D23 | `per` divides; it does not multiply by its reciprocal | `10,000 / 3` and `10,000 * (1/3)` differ in the last place, and the hours rule exists so the last place survives to the total. |
| D24 | The rounding rule is per item and per step, and `exact` does not settle | Rolls and sheets round up while fastener plates order at a fraction, because that is what the supplier bills. Settling exists to protect a rounding decision from binary crumbs; applying it where nothing is being rounded only throws precision away — and hours run through that step. Addendum 2 §2 and §3. |
| D25 | An order step that was started but never given a conversion prices nothing, and says so | It used to fall back to pricing the estimating unit, which prices membrane by the square instead of by the square foot and looks entirely plausible on the sheet. Found while testing the three-unit chain. |
| D26 | Adders within a class are each taken on the class subtotal and summed — they never compound | Confirmed against both real recaps: tax and escalation sit side by side on subtotal material. Compounding them puts a job several thousand dollars out. Addendum 2 §5. |
| D27 | The comparison derives the profit rate from the printed dollars and reports it, rather than failing a line on the printed rate | A report prints its rate to two places and its dollars to the cent, and two places is not always enough to reproduce the dollars. One of the two fixture jobs is exactly that case. The dollars are what happened. Addendum 2 §4. |
| D28 | The fixture comparison prints two forms: the full table, and a shape with no figures in it | The figures are a client's. The shape — which rows were checked, and whether each was within a stated tolerance — is the only form fit to go anywhere public, and a result that says only "pass" is not evidence. |
| D29 | The client-data gate is a pre-commit hook, not a habit | Twice a real figure went into the public tree because it was in front of me while writing a test and made the test feel real. It reads what is in `fixtures/` and `refs/`, builds the set of figures distinctive enough to identify a job, and refuses any commit carrying one out. Turn it on with `git config core.hooksPath .githooks`. Addendum 3 §2. |
| D30 | A token must be distinctive to count: at least four digits, and a bare integer that is a round hundred does not count | The rule as written — every number with a decimal point — fires on `1.5` and `2.00`, and a twenty-thousand-dollar quote is indistinguishable from a probe timeout. A gate that fires on everything gets switched off within a week. Universal roofing constants (pitch factors) are excluded by name. Stated in the script. |
| D31 | The subtotal rebuild prices every line THROUGH the engine, and separates lines whose chain the report fully states from lines whose conversion had to be recovered from the money | Summing the report's own net-cost column would check the parser and prove nothing about the pricing. A line whose conversion is recovered from the printed money cannot also be evidence that the money is right, so it is counted apart and never allowed to look like a pass. |
| D32 | The per-line tolerance is derived from display rounding, not flat | A report DISPLAYS an order quantity to two places and computed the money on the unrounded one. Feeding the displayed figure back can be out by half a hundredth of a unit's price. This is addendum 2 §3's rule about hours, and it turns out not to be only hours — it applies to boxes and cartons too. |
| D33 | `CLAUDE.md` at the repo root carries the never-list and the reporting cadence | A session does not remember the last one; the repository does. Addendum 3 §3. |
| D34 | Selection lives in the window, not in the job | Which condition you are looking at is not part of the bid. Saving it would put a line in a git diff every time anybody clicked anything. One selection, watched by the tree, the rail and the sheet — the same reason there is one document. |
| D35 | Every area carries its own tear-off button, and the tree is hidden rather than absent in a torn-off window | A torn-off editor is not a lesser window; it is the same anatomy with the tree folded away. One sidebar button that tore off one particular editor was probe scaffolding in the product's chrome. Spec v2 §1.3. |
| D36 | Icons are drawn inline from Lucide's geometry, and never appear without their word | The policy allows this program no network, and an icon that arrives as part of the page cannot fail to arrive. A roofer should not have to learn a pictogram to find the line tool. |
| D37 | A measure with no number yet is an em dash with the reason in its tooltip — never a coloured word | Red says "something is broken". Nothing is broken: the sheet has not been scaled. Spec v2 §1.6. |
| D38 | The condition palette is twelve hues, and the interface has exactly one accent that is not among them | A colour that means "selected" on Tuesday must not mean "parapet" on Wednesday. Condition colour identifies a traced thing and nothing else. Spec v2 §1.4; the palette itself is my call, pending v1 §6. |
| D39 | Row actions sit in a column pinned to the right edge; the sheet scrolls inside its own area | A torn-off sheet is narrower than the table, and a delete button that scrolls off the edge is a delete button nobody can reach. Spec v2 §1.9. |
| D40 | The explanatory paragraph became the editor's help page, reached by the "?" in its header | Self-explanatory means the structure explains itself. A paragraph under a title on every open is what a help sheet is for. Spec v2 §1.10. |
| D41 | Traces are recorded one at a time, in order | Three quick counts used to start three conditions: each click read the job before the one before it finished writing, saw nothing selected that took a count, and made its own. Found by the section 1 probe after the restyle. |
| D42 | A run shows no square-foot measure at all, rather than showing a dash for one | A run has no surface (D3), and "— SF" beside it suggests it might have one if you scaled the sheet. Each kind shows the measures it actually has. |
| D57 | The 3D view is an editor type in the area picker, not a window of its own kind | Addendum 4 §4 leaves where it lives as a code call, between its own window and a view on the drawing. Appendix A3 and A4 already answer it: every area carries an editor-type selector at its top-left and a Tear off button at its top-right, and a torn-off window is the same anatomy with the tree folded away. So 3D is another editor, it can sit in any area, and it tears off to the second monitor by the mechanism that already exists — no new window kind, and nothing to build for it that section 1 did not already build. |
| D58 | The ruling documents are restored to `refs/` from the pastes that carried them, and `refs/` is the only place they live | The continuous Build Handoff — the document every addendum amends by section number — was never written to disk. It survived in the CLI's paste cache, which is a scratch area that nothing guarantees. A clone had the proposal, the open-ended handoff and the addenda, and no authority document to read them against. Restored byte-identical, not paraphrased, and checked with `diff` against the paste that carried it. |
| D59 | Light and dark are **ruled** to be a toggle; light is the default today and **the dark theme is not built** | Ruled by Patrick — "a toggle like every major construction software is." It was never the collision it appeared to be: v2 §2 already said dark can return as an option and is not the product's face, so v2 set the default and the design bundle supplies the option. Nothing in sections 1, 2 or 7 was built wrong. The work it creates — lifting colours into a two-theme token set across every editor — **has not been done**, and this entry originally read as though it had. There is one palette on `:root`, no toggle and no `prefers-color-scheme` query. Q5 is closed as a ruling; the build is outstanding. |
| D60 | `EDGE MASTER TEMPLATE.xlsx` is the library's column shape; `WATERTIGHT/MASTER_ROOFING_ESTIMATE_TEMPLATE.xlsx` is the recap flow. They are not rival authorities | Checked by opening both. The EDGE workbook is one sheet of ~2,190 item rows carrying the order and price formula chain; the WATERTIGHT workbook is six sheets running takeoff into material and labour into a recap — the structure section 3 already built and verified. One is a catalogue, the other is the machine. Both are named with their roles in Addendum 5 so the question cannot be re-asked. Closes Q8. |
| D61 | The restored Build Handoff is corroborated on every section a second witness exists for, and §3 and §4.1–§4.9 have none | The web seat recovered §4.10, §4.11, §4.12, §5, §6 and §7 from conversation history; all six match the disk copy verbatim, so the restoration is sound where it can be checked. It declined to reconstruct the sections it could not witness, which was right — a document that reads canonical and is partly invented is worse than a gap, because the gap is visible and the invention is not. Those sections stay single-source, and that is recorded rather than resolved. |
| D63 | Where a tree has an index or a manifest, that is the first read, not the last | `~/KNOWLEDGE` carries `INDEX.md`, `index/knowledge_manifest.{csv,json}` (1,122 rows), `index/index_audit.md` and the script that built them. A survey of that tree was written without opening any of it, and reported five categories as gaps that had to be authored from nothing. Re-run against the manifest, the single largest `doc_type` in the corpus is `detail_drawing` at 655 rows — the class the survey called absent. The manifest is CSV and JSON, so it needs no model and no retrieval service; the cost of reading it was one command. |
| D64 | The NRCA CAD details are usable on this box and nothing derived from them ships | `License Agreement for electronic.pdf` sits in the folder with the drawings and is explicit: a "personal, nontransferable and nonexclusive license to use… on a single personal computer", "You may not transfer, sell, lease or distribute copies of this software to others", and the contents are NRCA's copyright. It also grants, in the same document, "You may use the drawing files and make modifications to suit your specific project requirements." So they inform an estimator's own work and a local library on this machine; a leg dimension read off a `.dwg` never enters the public tree. Same shape as the rule already governing `EDGE MASTER TEMPLATE.xlsx`: the knowledge is usable, the content is not distributable. |
| D65 | Section 6 takes no straight-skeleton dependency — **superseded in part by D71, which is what shipped** | Two findings, both from search. First, licence: CGAL's `Straight_skeleton_2` is **GPL** (not LGPL), `Botffy/polyskel` is LGPL-3.0, `ladybug-geometry-polyskel` is AGPL-3.0, no permissive Rust crate exists, and the one npm package labelled MIT ships a WebAssembly binary compiled from that GPL CGAL code — an MIT label over a copyleft artefact, which is a risk to refuse rather than resolve. Second, and it is the one that matters: **§4.10 never asked for a straight skeleton.** Facets are traced, not generated from a footprint. What it needs is "which drain does this point fall to, and where is the valley between two drains" — that is a nearest-site partition, and the ridge `between` two drains is a Voronoi edge. `d3-delaunay` (ISC) with `polygon-clipping` (MIT), or `spade` with `geo` (MIT/Apache-2.0) on the Rust side, are permissive, offline and bundleable. If hip-and-valley generation from a bare footprint is ever wanted it is a different feature, and the route is porting the algorithm from an Apache-2.0 or MIT reference, never taking the package. |
| D66 | Authorship, validity and firmness are three orthogonal axes on a quantity, not one scale | The design bundle's contract says every quantity is `derived` or `typed` with "no third state" — and its own escape hatch proves that governs **authorship only**: a value needing both becomes a formula whose inputs each carry provenance. "Nothing is ever silently zero" governs a different axis, **validity** — usable, pending, excluded, no price. NEXUS ships a third, **firmness** — firm, budget, estimate, placeholder — about how good a price is. A typed quantity can be excluded; a derived one can be pending; a firm price can sit on a pending quantity. Collapsing any two loses something an estimator acts on, and the apparent contradiction between the bundle and this program was one axis being read as all three. |
| D67 | The screen says **girth**; `STRETCHOUT` stays the formula name; both words, and `flat width` / `developed width`, parse on import | Searched rather than assumed, and the assumption was half wrong. **Girth** is the spec-facing word: a gutter glossary defines it as "the width of the blank strip from which a profile is rolled", public `07 62 00` templates size gutter gauge by girth ranges, and ARCA's manual uses it for parapet cap width. **Stretch-out** is the shop-floor and pattern-development word, general to sheet metal rather than particular to roofing — and the claim that coping is *specified* by stretch-out could not be found in any source, so it is not repeated here. They measure the same thing from two rooms of the same shop. The screen takes the word a specification uses; the formula language keeps `STRETCHOUT`, because renaming an identifier that section 1 shipped buys nothing. **Everything parses on import**, because a supplier quote arrives in the trade's word and a quote that fails on a synonym is a silent zero wearing a different hat. |
| D69 | Tapered layout conventions are **researched and recorded, not implemented** — they are section 4's work | Two freely readable sources — a Construction Specifier article and a Garland technical PDF — converge independently on the same numbers, and both attribute them to NRCA practice rather than to themselves: a 4×4 ft board module, ½ in. minimum at the low edge and 4 in. maximum per board, ¼ in./ft as the standard slope with 1/16 to ⅜ available as special order, a 4×4 ft sump where insulation at the drain is ≤2 in. and 8×8 ft where it is ≥3 in., cricket slope at twice the field slope, and a cricket length-to-width ratio of about 3:1 to 4:1. Convergence across independent sources attributing to a third is the mark of shared trade convention rather than one company's expression, so the logic is implementable — **which is not the same as implemented, and the original wording of this entry claimed it was.** What exists today is the four-inch board maximum and a cricket that takes its own slope. The rest — the half-inch minimum, the special-order range, the sump threshold, the board module, the length-to-width ratio, and a cricket slope derived at twice the field's — is section 4's work, done deliberately. Implementing seven trade rules in a hurry to make a sentence in this ledger true would be the wrong reason to build them. The vendor's own loading charts and branded diagrams are that vendor's expression and are not copied. Carlisle's, GAF's and Versico's tapered guides are variously 403-blocked or behind a login, which is its own answer about what may be redistributed. |
| D70 | `Kentucky-ai/opentakeoff` is the provenance reference; `protakeoff`'s licence is unconfirmed and it is not a dependency candidate | opentakeoff is Apache-2.0 verified through the GitHub API, actively developed, and its README states the record this program has been designing from scratch: every shape stores the scale it was measured at, the method that produced it, whether a human corrected it, and the machine's original boundary frozen beside the correction. That is D66's authorship axis with an audit trail attached, and it is worth reading before section 4. protakeoff matches this program's stack almost exactly — Tauri 2, Rust, TypeScript, SQLite — and its README shows an MIT badge, **but GitHub's licence API reports none specified and no LICENSE file is in its tree**. A badge is not a grant. Read for its two-level assembly shape; take nothing from it until a real licence appears. OpenConstructionERP is AGPL and therefore reference only, but its pattern is directly applicable: classification codes arrive as user-imported data rather than shipped taxonomy, which is how this program already avoids shipping CSI text. |
| D68 | Recognized and declined, so no seat builds them as a favour | The design bundle names four things it deliberately did not design: a drain-sizing check against roof area and rainfall rate, an insulation board layout or cut sheet for the supplier, bid comparison against a previous job's cost per square, and ponding simulation over time. The last agrees with §4.10 independently — the ponding view marks local minima that are not drains, it does not model water. Recording a recognition that was not built is the difference between a decision and an omission. |
| D71 | The heightfield is sampled on a grid and the nearest drain is a loop, so section 6 ships three.js and nothing else | D65 ruled out a straight skeleton on licence and on need. Building it confirmed the second half: what the view actually asks is "how thick is the roof here", which is the start thickness plus the slope times the distance to the nearest drain. A roof has a handful of drains, so that is a loop, and the answer is exact. A Voronoi library would give the exact *boundary* between two drains' basins, and a sampled surface never needs one. `d3-delaunay` and `polygon-clipping` stay in `DEPENDENCIES.md` as evaluated-and-not-needed so nobody prices the question twice. |
| D72 | A no-fall region is where the boards run out, not where a solver says water pools | Ponding had to mean something an estimator can act on. A tapered stack cannot build for ever — four inches is the most a single board carries — so a field can only rise so far before it goes flat, and flat is where water stays. That gives the mark a cause an estimator recognises and a number they can price, and it falls straight out of `T`, `TAPER` and `BOARDS`, which are already on the condition. It is also the boundary §4.10 and the design bundle independently drew: mark where fall runs out, do not simulate water over time. |
| D73 | A cricket's ridge is traced, and `between` records which drains it serves rather than generating it | §4.10 calls a cricket a ridge line between drains and two planes. The line could be solved for — it is a skeleton edge — but every other surface in this view is derived from something a person drew, and a generated ridge would be the one piece of geometry the estimator cannot correct. So the ridge is a line condition with a role, the two planes fall square off it by its width and slope, and `between` is provenance. |
| D74 | A window knows it was torn off by its own label, not by which editor it is showing | Found by section 6's check, and it had been latent since section 1. The page read "am I detached?" as "is my editor not the Plan", which is a different question — so the moment an area's editor picker was used in the main window, the window decided it had been torn off and dropped the tree and the menu bar. The shell names the first window `main` and names a torn-off one after its editor, so the label is the fact. The front-end harness has no shell to ask, and falls back to the URL there, which is the only thing that distinguishes one stubbed page from another. |
| D62 | "NEXUS" is always written with a path, because there are two of them | `~/projects/nexus-phase0/viewer/` holds the three-axis model — `AxisValue`, `Authority`, and a shipped `Confidence` colour language. `~/projects/buildos-world/shell/nexus-standalone.html` holds the fifteen-field task editor. §4.12's nine-field list is drawn from the second and drops five of its fields. Naming the product without the path already sent one seat to the wrong artifact looking for a field set. |
